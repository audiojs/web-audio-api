Web Audio,
without the browser.

Run the same audio graph in Node, CI, servers, scripts, and the browser. No new audio API. No native dependency setup.

$ npm install web-audio-api

Pure JavaScript · ESM · Node 18+ · MIT

Basic usage 
import { AudioContext } from 'web-audio-api' // Node
// Browser: const { AudioContext } = globalThis
// CI: import { OfflineAudioContext } from 'web-audio-api'

const ctx = new AudioContext()
await ctx.resume()

const osc = ctx.createOscillator()
osc.frequency.value = 440
osc.connect(ctx.destination)
osc.start()

Testing in CI

OfflineAudioContext renders into memory. Test samples, peaks, spectra, duration, or hashes without a browser or speaker.

import assert from 'node:assert/strict'
import { OfflineAudioContext } from 'web-audio-api'
import { buildTone } from './examples/_portable.js'

const ctx = new OfflineAudioContext(1, 44100, 44100)
buildTone(ctx, { when: 0, duration: 1 })
const audio = await ctx.startRendering()

let peak = 0
for (const sample of audio.getChannelData(0))
  peak = Math.max(peak, Math.abs(sample))
assert.ok(peak > 0.2)

Tone.js in Node

The polyfill installs the globals used by browser-oriented libraries. Import Tone after it so its constructor checks see WAA.

import 'web-audio-api/polyfill'
const Tone = await import('tone')

Tone.setContext(new AudioContext())
const synth = new Tone.Synth().toDestination()
synth.triggerAttackRelease('C4', '8n')

Why the dynamic import?

Static imports are hoisted. Tone would inspect globals before the polyfill installs them.

For a static Tone import, start Node with:

node --import web-audio-api/polyfill app.js Read the complete recipe →

JZ and WebAssembly

JZ compiles a numeric JavaScript subset to small WASM modules. The direction is to move hot DSP kernels into the realtime/worklet lane without asking library authors to rewrite them in Rust or AssemblyScript.

Today
pure JS graph and DSP
Next lane
selected hot kernels in WASM
Status
experimental, not a latency guarantee

Limits

  • Native bindings remain the better choice when maximum heavy-DSP throughput is the only criterion.
  • AudioWorklet currently runs synchronously. Production low-latency WebRTC mixing is promising, not yet the headline promise.
  • Browser demos use the browser’s native engine; they prove graph portability rather than pretending the package replaces a browser engine.

FAQ

Short answers with links to runnable examples and complete guides.

Why does AudioContext start suspended?

AudioContext starts suspended to match the Web Audio lifecycle. In Node, call await ctx.resume(). Browsers may require that call inside a user gesture.

How do I close the audio output?

Call await ctx.close(). Explicit resource management is also supported with using ctx = new AudioContext().

Can I test audio without speakers?

Yes. Build the graph in an OfflineAudioContext, await startRendering(), then assert the returned AudioBuffer.

Does it run Tone.js?

Yes. Import web-audio-api/polyfill before dynamically importing Tone, or launch Node with --import web-audio-api/polyfill.

Which file formats can it decode?

decodeAudioData() uses audio-decode for WAV, MP3, FLAC, OGG, and AAC inputs.

How does microphone input work in Node?

Install the optional audio-mic package, then use getUserMedia() through the polyfill or push PCM into a CustomMediaStreamTrack.

Is it fast enough for realtime work?

All included benchmark graphs render faster than realtime. Simple graphs compare well with native bindings; heavy DSP is slower. Worklet thread isolation and the JZ/WASM kernel lane are active boundaries.

Is this a DAW, framework, or new Web Audio tutorial?

No. The W3C standard is the API, and MDN remains the general browser reference. WAA exists so those graphs can run where a browser is absent; this site stays focused on executable library recipes.
